# CLAUDE.md

Scoped to `day6/shopping/`. Repo-wide tooling and conventions are in the root `CLAUDE.md`.

## What this is

"쇼핑리뷰분석" (`쇼핑리뷰분석_PRD.md`): a free Manifest V3 Chrome extension for marketers/sellers. On a Coupang or Naver Smart Store product page, the user clicks "리뷰 분석하기" and the extension parses reviews from the page DOM, sends them to a Gemini-backed proxy for sentiment/insight/keyword analysis, and renders a popup dashboard (donut chart, 5-line insight summary, keyword mindmap, color-tagged review list) plus an Excel export.

The MVP was built for **Coupang and Naver simultaneously** (not staged one-platform-first), per an explicit decision when this was planned.

**Current honest state: real DOM parsing is live-verified on Coupang (single-page collection works end-to-end through a real Gemini/proxy round trip); Naver is still only verified against a hand-captured snippet, never run live.** `extension/lib/config.js`'s `PROXY_BASE_URL` fetch was initially broken by a missing `http://localhost:3000/*` entry in `manifest.json`'s `host_permissions` — MV3 background fetches to origins outside `host_permissions` get normal browser CORS enforcement, and the proxy sends no CORS headers, so it failed as `TypeError: Failed to fetch`. Fixed by adding the entry (see the "project-hub / deployment" note below — this must be swapped alongside `PROXY_BASE_URL` on deploy). Coupang pagination initially stalled after page 1 (only 10 reviews collected) because `nextButton.click()` doesn't reliably trigger React components that bind to pointer/mouse events instead of `click`, and `MutationObserver`-based change detection can miss React reusing DOM nodes and only patching text. Fixed by `ShoppingReviewCommon.simulateClick` (dispatches a full pointerdown/mousedown/pointerup/mouseup/click sequence, in `content-scripts/common.js`) plus direct polling of the review-id sequence instead of `waitForMutation` (both `coupang.js` and `naver.js`'s `advanceReviews()` now use this pattern). Both files' header comments say exactly what was/wasn't checked — read those before trusting either. In short:
- `extension/content-scripts/coupang.js`: item selectors (rating/date/text/option) verified against a real product page's review `<article>` markup, and a real run confirmed page-1 parsing + the proxy round trip. Multi-page collection (>10 reviews) was broken (see above) and is now fixed with `simulateClick` + review-id polling, but **that fix itself hasn't been confirmed live yet** — the original live run never got past page 1. Product-name extraction (`h1`/`document.title` fallback) is still unverified guesswork.
- `extension/content-scripts/naver.js`: item selectors verified against a real product page's review **preview widget** (`#REVIEW`, top ~8 reviews only) *and* against the actual "리뷰 전체보기" modal (`#REVIEW_LIST_TOP` > `#REVIEW_LIST`, hand-captured with 708 reviews on the same product), but the extension itself still hasn't been run live in Chrome. The modal's markup turned out meaningfully different from the preview widget — items are `<li id="REVIEW_ITEM_{contentsId}">` instead of `<a data-shp-contents-id>`, rating has no "평점" label text (just a number after the star svg), and review text/option live under stable `id="review_content_{id}"`/`id="review_option_{id}"` anchors rather than the widget's hashed classes — `findReviewItems`/`extractRating`/`extractReviewText`/`extractOption` now each try the modal shape first, falling back to the widget shape. The user confirmed the modal loads more reviews on scroll, not a "더보기" button or numbered pages, so `advanceReviews()`'s scroll fallback now scrolls the nearest actually-scrollable ancestor of the last review item (found via computed `overflow-y`) instead of `document.body` — but since this was reasoned from static HTML (computed styles aren't visible in a pasted snippet), whether that scroll actually triggers more reviews to load is still unconfirmed. This is still the shakier of the two implementations and the most likely to need adjustment once seen live.

DOM structure for both was verified from manually-pasted HTML snippets, not live browser automation (claude-in-chrome blocks both coupang.com and smartstore.naver.com), but the pipeline as a whole — popup → background → content script → proxy → Gemini(mock) — has now been run live once, on Coupang, by the person using the extension. Everything else (proxy, background state machine, popup UI, xlsx export) has additionally been exercised with `MOCK_ANALYSIS=1` mock data and passes `npm run build`. Before trusting a change, load the extension unpacked and click through it by hand on a real product page (see "Checking your work").

## Why this folder is different

Two sub-projects under one parent folder:
- `extension/` — the Manifest V3 extension itself. Plain JS/CSS/HTML, no build step, no `package.json`.
- `server/` — a Next.js proxy (own `package.json`, see `server/CLAUDE.md`), whose only job is holding `GEMINI_API_KEY` server-side so the extension never ships it to the browser (same reasoning `day5/news` and `day6/dust` already established for their own API keys).

Unlike `day5/news`/`day6/dust`, these two halves are **not** independently useful — nobody visits `server/` as a website, and `extension/` is dead on arrival without it. Despite being two folders/technologies, treat them as one shippable unit. The extension calls the proxy by a hardcoded base URL (`extension/lib/config.js`'s `PROXY_BASE_URL`, currently `http://localhost:3000`) rather than any service discovery.

## Tooling

- `extension/`: `chrome://extensions` → enable 개발자 모드 (Developer mode) → "압축해제된 확장 프로그램을 로드합니다" (Load unpacked) → select `day6/shopping/extension/`. No build step, no auto-reload — after editing a file, click the extension's reload icon on `chrome://extensions` (and refresh any open product-page tab, since content scripts only re-inject on page load).
- `server/`: see `server/CLAUDE.md` — `npm run dev` on localhost:3000 must be running for the extension to get real responses (mock or real Gemini).

## Architecture decisions

- **Background service worker owns state, popup is a thin renderer.** Analysis can take up to ~30s (PRD §4), long enough that a user plausibly closes the popup mid-flight — that kills any work happening in the popup's own document. `extension/background.js` runs the full orchestration (detect platform → message the content script → POST to the proxy) and persists `{status, platform, productName, progress, reviews, result, errorCode, errorMessage}` to `chrome.storage.session` at every step (`status` ∈ `idle|parsing|analyzing|done|error`). `extension/popup/popup.js` reads that state on open and re-renders on `chrome.storage.onChanged` — closing/reopening the popup never loses in-progress or completed work.
- **Message passing**: popup → background is `chrome.runtime.sendMessage({type:'START_ANALYSIS'})` (immediate ack only, real progress comes via storage). Background → content script is `chrome.tabs.sendMessage(tabId, {type:'PARSE_REVIEWS', targetCount: MAX_REVIEWS_TARGET})` (`extension/lib/config.js`, currently 150 — lowered from 300, see `server/CLAUDE.md`'s "Not built yet" for why); content scripts also fire one-way `{type:'PARSE_PROGRESS', count, target}` messages while collecting, relayed into storage. If `chrome.tabs.sendMessage` fails with "Receiving end does not exist" (a real, common case right after the extension is installed/reloaded on an already-open tab), background falls back to `chrome.scripting.executeScript` to inject the content-script pair on demand and retries once.
- **Content scripts are split per site** (`content-scripts/common.js` shared helpers + `coupang.js`/`naver.js`), each scoped by its own `matches` pattern in `manifest.json` — Coupang selector logic can never accidentally run against a Naver DOM. `common.js` exposes `window.ShoppingReviewCommon`: dedupe-by-hash, a generic `collectReviewsLoop`, `waitForMutation` (available but currently unused by either site script — see below), and `simulateClick` (dispatches a full pointerdown/mousedown/pointerup/mouseup/click sequence rather than calling `.click()`, because pagination/load-more buttons on both sites are React-driven and a bare `.click()` doesn't reliably trigger components bound to pointer/mouse events). Both site scripts' `advanceReviews()` click via `simulateClick` and then confirm the page actually changed by polling a review-id signature directly, rather than relying on `MutationObserver` — the latter can miss cases where the framework reuses existing DOM nodes and only patches their text.
- **"다른 상품 분석하기" reuses `START_ANALYSIS`, no separate reset message.** `popup.js`'s `resultView` has a button that calls the same `startAnalysis()` as `startButton`/`retryButton` — it re-runs the full orchestration against whatever tab is currently active. The user is expected to navigate to a different product's page first, then click it; `background.js`'s `orchestrate()` already resets all state fields at the start of every run, so no explicit "clear to idle" step was needed.
- **Chart/mindmap are hand-rolled inline SVG** (`extension/popup/render/donutChart.js`, `mindmap.js`) — no charting library, given there's exactly one donut and one 5-8-node graph. Matches the repo's no-framework default and avoids any MV3 CSP question. Every sentiment color also carries a text label (positive/neutral/negative badges in `reviewList.js`, emoji+label in the donut legend) — never color alone, following `day6/dust`'s accessibility convention.
- **Excel export is vendored SheetJS**, not CDN-loaded — MV3's CSP blocks remote script execution. `extension/vendor/xlsx.full.min.js` was downloaded once from `cdn.sheetjs.com` (xlsx 0.20.3) and is loaded via a plain `<script src="../vendor/xlsx.full.min.js">` tag in `popup.html`, a same-extension local resource load the CSP doesn't restrict. `extension/popup/render/xlsxExport.js` builds one sheet (번호/리뷰원문/별점/작성일/옵션/감성라벨/키워드태그 — the PRD's "리뷰 원문 + 감성 라벨 + 키워드 태깅" requirement) and triggers `chrome.downloads.download()` on a `Blob` URL.
- **Gemini response includes per-review keyword tags**, not just a global keyword list — `AnalyzeResponseBody.reviewLabels[].keywords` (an array of keyword ids). This is a small addition beyond the original planned contract, needed so the xlsx export's "키워드태그" column can be populated per row; see `server/src/types/analyze.ts`.
- **Icons are a generated placeholder** (`extension/icons/icon{16,48,128}.png`) — a flat blue speech-bubble mark, produced by a one-off script, not designed. Fine for local testing; revisit before any real distribution.

Naver's pagination (`advanceReviews()`'s three-way guess: "리뷰 전체보기" → "더보기" button → scroll) is the shakiest part of either implementation and the most likely to need rework once observed live. **This is the single biggest remaining gap** — until a real run happens, treat both as "probably works, definitely hasn't been proven."
- **Live in-Chrome UI verification.** The popup/background/proxy round trip was verified via `curl` against the mock proxy and `node --check` syntax validation only — never actually loaded as an unpacked extension and clicked through. Do this before considering the UI "done" (see "Checking your work").
- ~~Real Gemini call verification~~ — done, see `server/CLAUDE.md`: a real key now lives in `server/.env.local` (`MOCK_ANALYSIS=0`) and a real `/api/analyze` call round-tripped correctly. Still unverified: latency/quality at a full 300-review payload (only tested with 5) and whether the extension's real Coupang/Naver-parsed reviews (as opposed to hand-written test text) analyze cleanly end-to-end.

- Everything PRD §9 explicitly excludes from MVP: URL 입력 자동 다중 수집, 경쟁사 비교 분석, 기간별/누적 트렌드 리포트, 대행사용 다중 클라이언트 관리, 별도 대시보드 탭.
- Review date normalization to a consistent ISO format (currently passed through as whatever string the content script extracts, once that exists).
- MV3 service-worker keep-alive hardening (the ~30s idle-kill risk during a long analysis) — not addressed; works today because chained `fetch`/`chrome.tabs` promises tend to keep the worker alive, but a `chrome.alarms`-based keep-alive would make this robust rather than incidental.
- Chrome Web Store packaging/publishing — entirely unstarted.

## project-hub / deployment — not done yet

- **Deployment**: needs a second Vercel project with Root Directory `day6/shopping/server`, plus `GEMINI_API_KEY` registered there as a real environment variable. Manual dashboard step, not scripted.
- Before distributing the extension to anyone else, `extension/lib/config.js`'s `PROXY_BASE_URL` must be switched from `http://localhost:3000` to the deployed proxy URL — **and** `extension/manifest.json`'s `host_permissions` entry for `http://localhost:3000/*` must be swapped to the same new origin (see config.js's comment; without a matching host permission, `background.js`'s `fetch()` to the proxy hits normal CORS and fails with `TypeError: Failed to fetch`, which is exactly what happened during local dev testing until the localhost entry was added).
- Chrome Web Store publishing is a separate, unstarted step (needs a real icon set, store listing, privacy disclosure for the reviews it processes).
- project-hub card registration (`project-hub/index.html`'s `PROJECTS` array) after the above — same pattern as `day5/news`/`day6/dust`'s still-pending entries.

## Checking your work

No test suite (nor could one meaningfully cover live DOM selectors). Before considering a change done:

```
cd server && npm run build     # type-checks + lints + production build
cd server && npm run dev       # localhost:3000, with MOCK_ANALYSIS=1 in .env.local
```

Then in Chrome: load `extension/` unpacked (see "Tooling"), open the popup, and manually verify:
- Idle state renders and the "리뷰 분석하기" button is clickable on a Coupang/Naver product page.
- On both platforms, clicking it should now attempt real parsing — **neither has ever been run live**, so check first whether it actually collects reviews and reaches `analyzing`, versus failing with `PARSE_ERROR`/`NO_REVIEWS_FOUND` (which would mean the selectors need fixing against whatever page structure Chrome actually renders). Naver is the higher-risk one — watch specifically whether `advanceReviews()` gets past the initial ~8-review preview widget at all.
- To verify the `done` dashboard (donut chart, insights, mindmap, review list, excel download) without real parsing: open the extension's service worker console from `chrome://extensions` and manually run `chrome.storage.session.set({shoppingReviewAnalysisState: {status:'done', productName:'테스트 상품', reviews:[...], result:{...}}})` with data shaped like `server/src/lib/mockResponse.ts`'s output, then reopen the popup.
- Excel download opens in a spreadsheet app with intact Korean text in all columns.

`curl -X POST http://localhost:3000/api/analyze` with a JSON body (`platform`, `productName`, `reviews[]`) against the mock proxy is a fast way to sanity-check the API contract without the extension at all — already confirmed working during implementation (Korean text round-trips correctly when sent via a UTF-8 file payload; inline shell `-d` arguments can mangle Korean text due to terminal/curl argument encoding, not a server bug — see root `CLAUDE.md`'s UTF-8 gotcha note).
