# DESIGN.md: 가게 길찾기

> 이 문서는 PRD.md를 기반으로 한 디자인 가이드다. 핵심 전제: **이 서비스는 고령자와 어린이도 이용한다.** 따라서 모든 디자인 결정은 "예쁨"보다 "명확함과 접근성"을 우선순위로 둔다.

## 1. 무드 (Mood)

### 1.1 전체 톤
**"동네 이웃이 알려주는 듯한 따뜻함"** 위에 **"표지판처럼 명확한 신뢰감"**을 얹은 구조.

- 기본 뼈대: 명확하고 안심되는 신뢰감 (표지판/안내판 같은 구조와 가독성)
- 그 위에 얹는 톤: 따뜻하고 친근함 (동네 이웃 같은 색감·표현)

### 1.2 우선순위 원칙
따뜻함과 명확함이 충돌할 경우, **명확함을 우선한다.** 조금 딱딱해 보이더라도 고령자·아동이 헷갈리지 않는 쪽을 선택한다. 따뜻함은 색상 톤, 문구, 일러스트 디테일 등에서 보완한다.

### 1.3 무드 체크리스트
디자인 산출물이 나올 때마다 아래 질문으로 검증한다.
- [ ] 이 화면을 처음 보는 70대 어르신이 3초 안에 "무엇을 눌러야 하는지" 알 수 있는가?
- [ ] 이 화면을 초등학생이 봐도 헷갈리지 않는가?
- [ ] 딱딱함보다 모호함이 더 위험하다는 원칙을 지켰는가?

## 2. 컬러 (Color)

### 2.1 컬러 팔레트

| 역할 | 색상 계열 | 설명 |
|---|---|---|
| **베이스 (Base)** | 차분한 그린 | 안정감, 신뢰감. 배경/보조 요소에 사용 |
| **서브 (Sub)** | 테라코타 | 따뜻함, 동네·길 이미지. 카드/일러스트 톤에 사용 |
| **강조 (Accent/CTA)** | 앰버·머스타드 노랑 (#E8A33D 톤) | 버튼, "길찾기" 등 핵심 액션에만 사용. 고시인성 색상으로 표지판·안내판에서 검증된 색 |

### 2.2 강조색 선정 이유
- 그린·테라코타는 중채도의 차분한 색이라 액션 버튼에 쓰면 눈에 띄지 않음
- 앰버/머스타드 노랑은 안내판·경고 표지판에 널리 쓰이는 고시인성 색으로, "여기를 봐야 한다"는 신호가 명확함
- **적록색약(가장 흔한 색약 유형) 사용자에게도 안전** — 그린 베이스에 빨간 계열 강조색을 얹으면 구분이 어려워지는 문제를 피함

### 2.3 접근성 원칙
- 텍스트와 배경 간 명도 대비는 **WCAG AA 기준(4.5:1) 이상**을 최소 기준으로 하며, 핵심 액션 버튼은 AAA 기준(7:1) 지향
- 색상만으로 정보를 구분하지 않는다 (예: "성공/실패"를 색으로만 표시하지 않고 아이콘·텍스트 병기)
- 강조색(앰버)은 버튼 등 실제 액션에만 사용하고, 장식 목적으로 남용하지 않는다 (남용 시 진짜 중요한 곳에서 주목도가 떨어짐)

## 3. 타이포그래피 (Typography)

### 3.1 서체
**둥근둥근한 고딕체 계열** (예: Pretendard, Noto Sans KR)
- 가장 무난하고 가독성이 검증된 선택
- 손글씨체·장식체는 사용하지 않음 (따뜻함보다 고령층 가독성을 우선하는 원칙에 따름)

### 3.2 글자 크기
**본문 기본 크기: 18~20px**
- 일반 웹 기준(16px)보다 크게 설정 — 고령층·저시력자를 고려한 접근성 권장 기준
- 정보량이 줄어들더라도 가독성을 우선

### 3.3 크기 위계 (제안 — 상세 설계 시 확정)
| 요소 | 크기(안) | 비고 |
|---|---|---|
| 헤드라인(H1) | 28~32px | 굵게 |
| 서브헤드(H2) | 22~24px | 굵게 |
| 본문 | 18~20px | 보통 굵기 |
| 버튼 텍스트 | 18~20px | 굵게, 본문과 동일하거나 크게 (버튼을 작게 만들지 않음) |
| 캡션/보조 텍스트 | 16px 이상 | 14px 이하는 사용하지 않음 |

### 3.4 타이포 원칙
- 자간·행간은 넉넉하게 (좁은 행간은 고령자·저시력자에게 특히 어려움)
- 굵기(font-weight)로 위계를 구분하되, 너무 얇은 굵기(Light 이하)는 본문에 사용하지 않음
- 한 문장은 짧게, 전문용어·줄임말 지양 (예: "위치 인증"보다 "정확한 위치 알려주기")

## 4. 레퍼런스 (Reference)

### 4.1 채택된 방향: 토스(Toss)의 정보 위계 구조
- **한 화면에 하나의 핵심 행동만 명확하게 제시**하는 구조를 우선 참고한다
- 여러 선택지를 한 번에 늘어놓기보다, 정보를 단계적으로 보여주고 사용자가 다음에 뭘 해야 할지 헷갈리지 않게 유도
- 버튼 크기와 터치 영역을 충분히 크게 확보 (오터치 방지, 고령자·아동 모두에게 유리)
- 색상보다 "레이아웃과 위계"로 중요도를 전달하는 방식 — 이 서비스의 "명확함 우선" 원칙과 직접 연결됨

### 4.2 참고했으나 채택하지 않은 사례 (기록용)
| 사례 | 참고 포인트 | 채택 여부 |
|---|---|---|
| 당근마켓 | "동네 이웃" 톤앤매너, 친근한 말투 | 무드(1장) 표현에는 일부 반영, 구조는 미채택 |
| 카카오맵/네이버지도 큰글씨 모드 | 버튼·텍스트 확대 구조 | 3장 타이포 크기 기준에 참고 |
| 지자체 어르신 전용 키오스크 UI | 강한 대비, 아이콘+텍스트 병기 | 2.3 접근성 원칙에 반영 |

### 4.3 향후 레퍼런스 보강 방향
- 실제 스크린샷/캡처본 확보 후 이 문서에 이미지로 첨부 예정
- 랜딩페이지 제작 단계에서 구체적 컴포넌트(버튼, 카드, 폼) 레퍼런스 추가 논의 필요

## 6. 화면 구성 (랜딩페이지)

> 아래 8개 섹션이 메인 랜딩페이지를 구성한다. 각 섹션은 1~5장에서 정한 무드·컬러·타이포 원칙을 그대로 따른다. PRD.md 8장이 요구한 6개 섹션(히어로·문제 공감·해결 방식·작동 방식·신뢰/차별점·푸터)을 모두 포함하고, 여기에 최근 리뷰와 서비스 특징을 더한 구성이다.
>
> **구현**: `day4/index.html` 단일 파일. Tailwind는 CDN으로 불러오고, 티커 애니메이션과 캐러셀 스냅만 `<style>` 블록에 직접 작성한다.
>
> **참고**: "길찾기"와 "최근 리뷰"는 가짜(더미) 데이터로 채워지며, 실제 데이터로 교체될 자리다. "서비스 특징"에 소개하는 AI 요약·챗봇·대시보드는 PRD.md의 기존 로드맵(4장)에는 없는, 이 랜딩페이지에서 새롭게 제시하는 미래 확장 기능이다. 추후 PRD 로드맵에도 함께 반영할지는 별도 논의가 필요하다.

### 6.1 히어로 (Hero)
| 항목 | 내용 |
|---|---|
| 목적 | 3초 안에 "무슨 서비스인지" 전달 |
| 구성 요소 | 서비스 이름("가게 길찾기") + 한 줄 소개 문구 + 검색창 |
| 핵심 액션 | **검색창** (가게/지역 검색 입력창 — 실제 서비스처럼 보이도록, 플레이스홀더 예: "가게 이름이나 동네를 검색해보세요") |
| 디자인 원칙 | 헤드라인은 굵게 32px(모바일)~40px(데스크톱) — 3.3절 H1 상한을 데스크톱에서만 넓혀 적용. 검색창과 검색 버튼은 높이 60px로, 최소 기준(44px)보다 넉넉히 잡아 고령자·아동도 쉽게 탭할 수 있게 함. 검색창 테두리/배경은 그린 베이스 위에서도 명확히 구분되도록 흰색 배경 + 진한 테두리 사용 |
| 부가 요소 | 헤드라인 아래에 등록 현황 3지표(등록된 가게·입구 사진·"도움이 됐어요" 수)를 두어 서비스가 실제로 쌓이고 있다는 인상을 줌 (더미 수치) |

### 6.2 문제 공감 (Problem)
| 항목 | 내용 |
|---|---|
| 목적 | PRD.md 8.1절의 검증 가설 "문제에 대한 공감이 실제로 존재하는가"를 확인하는 자리. 해결책을 보여주기 전에 먼저 "내 얘기네"라고 느끼게 함 |
| 구성 요소 | 헤매본 상황 3가지를 큰따옴표 인용문으로 제시 (건물을 두 바퀴 돈 경험 / 층을 잘못 알아 지각한 경험 / 핀과 실제 입구가 다른 경험) |
| 디자인 원칙 | 서브 컬러(테라코타) 톤의 카드로 따뜻하게 처리 — 문제를 지적하는 섹션이므로 경고색(앰버)을 쓰지 않는다. 인용문은 본문보다 굵고 크게(18px 굵게) 두어 한눈에 읽히게 함 |
| 마무리 | "가게 길찾기는 바로 이 순간을 없애려고 만들었습니다" 한 문장으로 다음 섹션(길찾기)에 연결 |

### 6.3 길찾기 (해결 방식)
| 항목 | 내용 |
|---|---|
| 목적 | 이 서비스의 핵심 가치(1.3절)인 "진짜 입구 정보"가 어떤 모습인지 실제 카드로 보여줌. 맛집 랭킹이 아니라 **입구 찾기 정보**가 주인공이다 |
| 데이터 | 가짜(더미) 데이터 5개 (연남동·을지로3가·성수동·강남역·망원동) |
| 레이아웃 | **가로 스크롤 캐러셀** (모바일에서 손가락으로 자연스럽게 넘기는 형태) + 아래에 "사진 → 설명 → 정확한 핀" 3단계 설명 블록 |
| 카드 구성 | 대표 이미지 자리, 동네·카테고리, 가게 이름, "정확한 위치 정보 있음" 뱃지(앰버), **입구 설명 문장**, "도움이 됐어요" 수, 길찾기 버튼(앰버) |
| 디자인 원칙 | 카드 간 간격을 넉넉히 두어 오터치 방지, 스크롤 힌트(카드 일부가 화면 끝에 살짝 잘려 보이도록)로 "더 있다"는 것을 시각적으로 암시. 길찾기 버튼은 높이 52px 이상 |
| 주의사항 | 섹션 상단에 "예시 데이터입니다" 캡션을 두고, 길찾기 버튼을 누르면 실제 지도 앱으로 연결되는 대신 데모 안내 메시지를 띄운다 (실제 서비스로 오해되지 않도록) |

### 6.4 작동 방식 (How it works)
| 항목 | 내용 |
|---|---|
| 목적 | 이용 흐름을 3단계로 축약해 "나도 쓸 수 있겠다"는 감을 줌 (PRD.md 8장 4번 섹션) |
| 구성 요소 | ① 가게를 검색합니다 → ② 입구를 확인합니다 → ③ 바로 출발합니다. 각 단계에 번호 배지 + 제목 + 1줄 설명 |
| 6.3절과의 차이 | 6.3의 "길찾기 정보는 이렇게 만들어집니다"(사진→설명→핀)는 **정보를 남기는 사람** 관점이고, 이 섹션은 **정보를 쓰는 사람** 관점이다. 둘을 나란히 두되 배경색(그린 풀블록 vs 흰 카드)과 문구로 확실히 구분한다 |
| 디자인 원칙 | 그린 베이스를 배경 전체에 깔아 앞뒤 섹션과 리듬을 다르게 함. 번호 배지에는 앰버를 쓰되 버튼이 아니므로 크기를 작게 유지. 흰 카드 위 본문으로 대비를 확보(흰 배경 위 진한 글자) |

### 6.5 최근 리뷰
| 항목 | 내용 |
|---|---|
| 목적 | 별점과 리뷰 한 줄이 흐르는 섹션으로, 서비스가 "살아있다"는 인상을 줌 |
| 구성 요소 | 별점(★) + 리뷰 한 줄 텍스트 + (선택) 작성자 닉네임 |
| 디자인 원칙 | 자동 흐름(마퀴/티커) 애니메이션을 쓰더라도 **속도는 느리게, 일시정지/호버 시 정지 옵션**을 두어 저시력자·고령자가 읽는 도중 놓치지 않게 함. 별점은 색상(노랑 별)뿐 아니라 숫자("4.5")도 함께 표기해 색약 사용자도 값을 알 수 있게 함 |
| 정지 수단 | 한 바퀴 60초로 느리게 흐르고, ① 마우스 호버 ② 키보드 포커스 ③ "리뷰 흐름 멈추기" 버튼 ④ 운영체제의 애니메이션 줄이기 설정(`prefers-reduced-motion`) 네 가지로 멈춘다. 호버를 쓸 수 없는 환경을 위해 버튼을 별도로 둔다 |
| 주의사항 | PRD.md에는 리뷰 작성 기능이 MVP 로드맵에서 제외되어 있음(4.2절). 이 섹션은 어디까지나 데모/더미 데이터이며, 실제 리뷰 기능 개발 여부는 별도 결정 사항 |

### 6.6 신뢰 / 차별점 (Why us)

### 6.11 에어비앤비 비주얼 언어 적용
> `day4/index.html`을 시각적으로 다듬는 2차 작업 기록. **채택한 것은 에어비앤비의 "레이아웃 언어"(카드 입체감·여백·곡률)뿐이고, 에어비앤비의 색상 정체성(코랄 #FF385C)은 채택하지 않았다.** 컬러 토큰, 폰트 크기 유틸리티, 서비스 로직(검색 폼 제출, 리뷰 티커 정지/재생, 데모 토스트)은 이 작업에서 전혀 손대지 않았다.

**채택한 것**
| 요소 | 이전 | 이후 |
|---|---|---|
| 카드 입체감 | `border-2` 실선 테두리 위주 | `shadow-sm`~`shadow-xl` 단계적 그림자로 대체(일부는 테두리를 얇게 남겨 유지) |
| 모서리 곡률 | 카드 `rounded-2xl`, 내부 요소 `rounded-xl` | 카드 `rounded-3xl`, 내부 요소 `rounded-2xl`로 한 단계씩 확대 |
| 여백 리듬 | 카드 패딩 `p-5`~`p-6` | `p-6`~`p-9`로 확대, 섹션 내부 그리드 간격도 `gap-5` 유지하되 카드 자체 호흡을 넓힘 |
| 호버 상태 | 상태 변화 없음(버튼 배경색만 전환) | 길찾기 카드·"서비스 특징" 카드·CTA 버튼에 `hover:-translate-y-*` + `hover:shadow-*` 조합으로 살짝 떠오르는 느낌 추가 |
| 헤더 | 정적 `border-b` | `sticky` + `backdrop-blur` + `shadow-sm`로 스크롤 시에도 떠 있는 느낌 |

**채택하지 않은 것 — 그리고 그 이유**
- **에어비앤비의 코랄(#FF385C) 강조색은 쓰지 않았다.** 2.2절에 정리했듯 이 서비스의 강조색(앰버 `#E8A33D`)은 "적록색약 사용자에게도 안전하다"는 이유로 선택된 것이다. 코랄은 빨강 계열이라, 그린 베이스(`base` 계열) 위에 얹으면 적록색약 사용자에게 정확히 2.2절이 피하려던 문제(그린과 빨간 계열의 저구분성)를 다시 불러온다. 에어비앤비 자체도 코랄을 초록 배경 위에 쓰지 않는다 — 그 조합을 우리 서비스에 가져오는 것은 레퍼런스의 형태만 빌리고 색의 이유는 무시하는 것이 된다.
- 색상 토큰(`tailwind.config`의 `base`/`terra`/`cta`/`ink`)과 모든 `text-[...]` 폰트 크기 유틸리티는 값을 하나도 바꾸지 않았다 — 3.2/3.3절의 크기 위계와 2.3절의 대비 기준을 그대로 유지하기 위함이다.
- 버튼의 액션 색상(앰버)은 여전히 실제 액션(검색·길찾기·도움이 됐어요)에만 쓰이고, 카드 그림자·곡률 같은 장식 변화는 색으로 정보를 구분하지 않는다는 2.3절 원칙과 무관하게 순수 입체감 표현으로만 사용했다.

**재사용 가능한 카드 패턴 (다음 작업자 참고)**
3장 "길찾기" 캐러셀 카드가 이번 리디자인의 기준 패턴이다. 실제 검색 결과 카드를 만들 때 아래 클래스 조합을 그대로 가져다 쓸 수 있다.
- 카드(`<article>`): `flex h-full flex-col rounded-3xl border border-base-tint/60 bg-white shadow-md transition-[transform,box-shadow] duration-200 hover:-translate-y-1 hover:shadow-xl`
- 이미지 영역: `relative h-40 overflow-hidden rounded-t-3xl` 안에 `<img class="h-full w-full object-cover">` + `absolute bottom-4 left-4`로 얹은 "입구 사진 N장" 뱃지 + `absolute bottom-1.5 right-2`로 얹은 저작자 표시 링크. 원래는 그라디언트 배경(`bg-gradient-to-br ...`)에 뱃지만 있었다가, 3장 "길찾기" 캐러셀의 예시 데이터 5곳에 처음엔 Lorem Picsum 더미 이미지(무관한 랜덤 스톡 사진)를 넣었는데, **실제 그 가게 사진**으로 바꿔달라는 요청을 받아 최종적으로 아래 방식으로 교체했다(2026-08-25). 진짜 검색 결과 카드(`renderPlaceCard` 등)는 아직 사진이 없어 이 이미지 영역 자체가 없다 — 자세한 내용은 아래 "예시 카드 실제 사진(Google Places Photos, 5곳)" 절 참고
- 본문 영역: `flex flex-1 flex-col p-6`
- 뱃지: `mt-3 inline-flex w-fit items-center gap-1.5 rounded-full bg-cta px-3 py-1 text-[1rem] font-extrabold text-ink shadow-sm`
- 주요 액션 버튼: `mt-4 h-[52px] w-full rounded-2xl bg-cta text-[1.125rem] font-extrabold text-ink shadow-sm transition-[transform,background-color,box-shadow] hover:-translate-y-0.5 hover:bg-cta-dark hover:shadow-md`
- 보조 링크(가게 상세 보기 등): `mt-3 block rounded-xl py-2 text-center text-[1rem] font-bold text-base-dark underline underline-offset-4 hover:text-cta-dark`
- **`transition-all`을 쓰지 않는다** — Vercel Web Interface Guidelines 점검(2026-08-25)에서
  지적된 뒤 위 두 항목을 `transition-[transform,box-shadow]`/`transition-[transform,background-color,box-shadow]`로
  바꿨다. `transition-all`은 명시하지 않은 속성(예: `outline`)까지 애니메이션 대상이 되어
  포커스 링 전환 등에서 의도치 않은 부작용을 만들 수 있다 — 새 카드/버튼을 만들 때도 실제
  바뀌는 속성만 나열할 것.

**예시 카드 실제 사진 (Google Places Photos, 5곳)**
3장 "길찾기" 캐러셀의 예시 데이터 5곳(네시사분·원조만선호프·밀도 성수본점·정돈 강남점·희옥)에 그 가게의 **실제 사진**을 넣어달라는 요청을 받았다. 검색할 때마다 라이브로 사진을 불러오는 방식은(6.13절 구글 리뷰처럼) 요청마다 과금되는 SKU라 비용이 들지만, 이 5곳은 정적인 예시 데이터라 **딱 한 번만** 받아서 파일로 저장해두면 그 뒤로는 비용이 전혀 들지 않는다 — 그래서 이 방식을 택했다.

| 항목 | 내용 |
|---|---|
| 받은 방법 | 일회성 스크립트(저장소에 남기지 않음)로 `places:searchText`(6.13절과 같은 Places API New)를 필드마스크 `places.photos,places.displayName`로 호출해 각 가게의 대표 사진 리소스 이름을 얻고, `{photo}/media?maxWidthPx=1000&key=...`로 실제 JPEG 바이트를 받아 `day4/images/{seed}.jpg`로 저장했다(2026-08-25, 5회 검색 + 5회 사진 요청 = 총 10회 호출, 그 이후로는 0회) |
| 저장 위치 | `day4/images/day4-yeonnam-cafe.jpg` 등 5개 파일, 저장소에 커밋한다(용량 약 1.4MB 합계). `.gitignore`의 `data/` 제외 규칙과는 무관 |
| 로컬 서빙 | `server.js`의 `STATIC_FILES` 화이트리스트에 5개 경로를 각각 추가했다(새 정적 파일을 추가할 때마다 이 화이트리스트도 챙겨야 한다는 "`STATIC_FILES` 화이트리스트" 메모 — day4/CLAUDE.md 참고). Vercel은 zero-config 정적 호스팅이라 화이트리스트와 무관하게 자동으로 서빙된다 |
| **저작자 표시(필수)** | Google Places Photos는 이용약관상 `authorAttributions`(사진 올린 사람 이름·프로필 링크)를 반드시 함께 보여줘야 한다. 각 카드 이미지 우하단에 `absolute bottom-1.5 right-2` 작은 링크로 "사진: {이름} (Google)"을 얹었다 — 클릭하면 그 기여자의 구글 지도 프로필로 연결된다. 사진을 나중에 바꾸거나 추가할 때 이 표시를 빠뜨리지 말 것 |
| 카테고리와 안 맞을 수 있음 | Places Photos는 그 가게에 달린 사진 중 첫 번째를 그대로 쓴다 — 대체로 입구·간판 사진이 나오지만("네시사분"은 실제 대문에 붙은 지번 문패까지, "정돈 강남점"은 벽돌 벽 브랜드 간판까지 나왔다), 매장 내부(주방 등)가 나올 수도 있다("밀도 성수본점") |
| 다시 받으려면 | 위 "받은 방법"의 스크립트를 다시 만들어 실행하면 된다(저장소에 남겨두지 않았으므로) — `.env.local`의 `GOOGLE_PLACES_API_KEY`만 있으면 되고, 텍스트 검색 쿼리는 "가게이름 + 정확한 주소"로 넣어야 동명이인 가게로 잘못 매칭되지 않는다 |

### 6.12 가게 상세 페이지 (`day4/place.html`)
> PRD.md 5.2절("위치 정보 보완/검증")이 설명하는 화면 — 한 가게에 대해 여러 사용자가 각자 남긴 사진·설명·정밀 핀이 누적되어 쌓이는 모습을 보여준다. **더 이상 정적 목업이 아니다**: `index.html`의 "길찾기" 카드나 검색 결과 카드의 "가게 상세 보기" 링크가 `id`(카카오 장소 ID)·`name`·`category`·`address`·`lat`·`lng`·`mapUrl`을 쿼리스트링으로 넘기고, 이 페이지는 그 `id`를 키로 `server.js`의 `/api/place-info` 계열 엔드포인트에서 실제 데이터를 읽고 쓴다 — 고정된 예시 가게("카페 모레") 하나만 보여주던 이전 버전과 달리, 쿼리스트링의 `id`가 바뀌면 완전히 다른 가게의 화면이 된다.

| 항목 | 내용 |
|---|---|
| 목적 | PRD 5.2절의 "자유 등록형 — 여러 사용자가 각자 추가, 모두 누적되어 표시됨" 구조를 실제로 동작하는 화면으로 구현했다. `id` 쿼리 파라미터가 곧 이 가게의 위치 정보(place-info) 저장 키다 |
| 구성 요소 | ① 가게 헤더(쿼리스트링에서 채운 이름·카테고리·주소·등록 현황 3지표, 서버에서 불러온 entries 기준으로 동적 계산) ② 정확한 입구 핀(실제 카카오맵 + 가장 최근 핀의 설명) ③ 사용자 제보 목록(entries 개수만큼 동적 렌더링, 각각 작성자·설명·사진(있으면)·"도움이 됐어요" 버튼·핀 포함 뱃지) ④ "당신도 도움을 줄 수 있어요" 단일 통합 제보 폼(닉네임·사진 URL·설명·핀을 한 번에 제출) ⑤ 푸터 |
| 사진 표시 방식 | 예전 버전에 있던 "입구 사진 갤러리(가로 스크롤, 7장)"라는 별도 집계 컴포넌트는 더 이상 존재하지 않는다. 사진은 각 제보 카드 안에 개별적으로 인라인 렌더링되며, 카드마다 최대 1장(그 제보에 첨부된 `photoUrl` 하나)만 보여준다. 이에 따라 `<style>` 블록의 `.snap-x-list`(가로 스크롤 캐러셀용, "사진 스트립: 가로 스크롤" 주석이 달려 있던 규칙)는 이 페이지 어디서도 쓰이지 않는 죽은 코드가 되어 삭제했다 |

| **카카오맵 도입 (§6.13/§6.14와 같은 종류의 새 외부 API 연동)** | 예전에는 격자무늬 CSS 플레이스홀더로 "지도 느낌만" 냈지만(실제 지도로 오인되지 않게 하려는 의도적 선택이었다), 사용자 요청으로 카카오맵 JS SDK 기반 실제 지도로 교체했다. 두 지도(정확한 입구 핀 표시용, 제보 폼의 핀 찍기용) 모두 이 가게 좌표를 중심으로 `level: 3`에 고정해서 띄우고 `draggable: false`·`zoomable: false`로 뷰를 잠근다 — 핀 마커가 진짜 `kakao.maps.Marker`가 아니라 기존 방식 그대로 `left`/`top` % 기반 CSS 오버레이라서, 지도를 움직일 수 있게 하면 마커 위치가 실제 지도와 어긋나 보이기 때문이다. 이 트레이드오프로 사용자가 지도를 둘러보며 확대·이동할 수는 없지만, 최소한 진짜 건물·도로를 보면서 클릭할 수는 있다. API 계약·도메인 등록 요건은 `day4/CLAUDE.md` "카카오맵 JS SDK" 절 참고 |
| 등록된 핀이 없을 때의 표시용 지도 | 사용자 제보 핀이 하나도 없으면 그 가게 좌표에 카카오의 기본 `kakao.maps.Marker`(빨간 물방울 아이콘)를 띄운다 — "아직 등록된 핀이 없습니다" 같은 별도 안내 문구는 두지 않는다(기본 마커 자체가 "일단 대략 여기"라는 참고점 역할을 하므로, 문구 없이도 지도가 비어 보이지 않는다). 첫 사용자 핀이 등록되는 순간 이 기본 마커는 자동으로 사라지고 CSS 오버레이 핀으로 교체된다 |
| **표시용 핀 — "가장 최근" 대신 평균 위치 (2026-08-25)** | 처음엔 가장 최근에 등록된 핀(`pinned[0]`, `created_at` 최신순)을 그대로 보여줬는데, 그 한 사람이 위치를 잘못 찍으면 지도가 그대로 틀리게 되는 문제가 있었다. 지금은 핀이 찍힌 제보 전체의 **평균 위치**를 보여준다 — `computeAveragePin()`이 전체 평균을 구한 뒤, 그 평균에서 `PIN_OUTLIER_THRESHOLD_PCT`(고정값 25, `pinX`/`pinY` 0~100 기준 유클리드 거리)보다 먼 핀은 **평균 계산에서만** 제외하고 나머지로 다시 평균낸다. 핀이 2개 이하면 어느 쪽이 "이상한" 핀인지 가릴 통계적 근거가 없어 이상치 판정 자체를 하지 않는다(3개부터 적용). 제외돼도 그 제보 자체가 지워지진 않는다 — 아래 목록엔 그대로 남고, 배지만 "📍 핀 위치 포함"에서 "⚠️ 핀 위치 포함 (평균과 차이 큼)"(`bg-terra-tint`/`text-terra`, `title` 툴팁으로 이유 설명)로 바뀐다. 지도 아래 설명 문구도 "N명이 표시한 위치의 평균입니다." 또는 제외가 있으면 "그중 M개는 ... 제외했어요."로 바뀐다 |
| **제출 시 "다른 분들과 너무 멀어요" 안내** | 정보 남기기 폼에서 핀을 찍어 제출하면, 그 핀이 **이번 등록 이전까지의** 핀 평균과 `PIN_OUTLIER_THRESHOLD_PCT`보다 멀 때 등록은 그대로 진행하되(입구가 실제로 여러 곳일 수도 있어 틀렸다고 단정하지 않는다) 성공 토스트 문구만 "등록되었습니다. 다만 표시하신 핀이 다른 분들 위치와 꽤 떨어져 있어요 — 위치를 다시 확인해 주세요."로 바뀐다. 위 평균 계산의 "3개부터 이상치 판정"과 달리, 이 비교는 기존 핀이 1개만 있어도 동작한다(그 하나와 비교하는 것 자체는 통계적 판단이 필요 없어서) |
| **핀 신고 (2026-08-25)** | 핀이 있는 제보 카드에만 "도움이 됐어요" 버튼 옆에 "🚩 핀 신고" 버튼을 둔다. `helpful`과 완전히 같은 패턴 — `place_info_entries.report_count`를 원자적으로 +1 하는 `increment_place_info_report()` RPC를 `/api/day4/place-info-report`가 호출하고, `localStorage`(`place-info-report:{entryId}`)로 같은 브라우저의 중복 신고만 막는다(로그인이 없어 근본적인 어뷰징 방지는 안 됨 — helpful/삭제와 같은 한계). **의도적으로 위 평균 위치 계산과 연동하지 않았다** — 신고는 참고용 신호일 뿐, 신고 몇 건이 쌓였다고 자동으로 평균에서 빼지 않는다(신고 접수 토스트에도 "다른 사람들의 평균 위치 계산과는 별개로, 참고용으로만 쓰여요"라고 명시). 자동 연동은 신고 남용에 취약해질 수 있어 이번 범위에서는 뺐다 — 필요해지면 별도로 다시 논의 |

### 6.13 구글 리뷰 섹션 (`day4/place.html`)
> PRD.md에는 이 기능 자체가 없다 — PRD 4.2절/8절이 언급하는 건 예시 데이터로만 채워진 index.html의 "최근 리뷰" 티커와, 보류된(post-MVP) "사용자가 직접 쓰는 리뷰" 기능뿐이다. 이 섹션은 그 어느 쪽도 아닌, 구글 지도에 이미 등록된 제3자 평점·리뷰를 가져와 보여주는 **완전히 새로운 기능**이며, PRD의 어떤 조항과도 어긋나지 않으므로("이탈"이 아니므로) PRD.md는 수정하지 않았다.

| 목적 | 가게 상세 페이지에서 카카오 정보만으로는 알 수 없는 구글 지도 평점·리뷰를 확인할 수 있게 한다 |

| 클릭 트리거 (자동 로드 아님) | 페이지 진입 시 자동으로 구글 API를 호출하지 않는다 — "리뷰 보기" 버튼을 눌러야 조회한다. 구글 Places API (New)의 평점/리뷰 필드는 호출당 과금되는 상위 등급 SKU라, 페이지를 열 때마다 자동 호출하면 보지도 않을 리뷰에 비용이 든다 |
| 150m 강제 반경 | 같은 상호명이 전국에 여러 곳 있을 수 있어, 카카오에서 넘어온 좌표를 중심으로 반경 150m(도보 약 2분) **안**에 있는 결과만 인정한다. 구글 Places API (New)의 `locationRestriction`은 `rectangle`만 지원하고 `circle`은 지원하지 않으므로(circle은 단순 "선호"인 `locationBias`에서만 가능), 서버(`day4/server.js`)가 좌표를 중심으로 한 정사각형 바운딩 박스를 계산해 보낸다. 대각선 방향으로는 최대 ~212m까지 포함될 수 있는 근사치이며, 이 근사로 인해 카카오·구글 두 서비스에 등록된 좌표가 크게 다른 가게는 실제로 존재해도 "찾을 수 없음"으로 나올 수 있다 |
| 필드 5개 제한 | `/api/day4/place-reviews`가 구글에 요청하는 필드마스크는 정확히 5개(가게 이름·별점·리뷰개수·리뷰·구글맵 링크)로 고정되어 있다 — 필드를 추가하면 과금 등급이 올라갈 수 있으므로 임의로 늘리지 않는다 |
| 못 찾음 상태 | 구글에서 매칭되는 가게를 못 찾으면 오류가 아니라 정상 응답(`{ found: false }`)으로 처리하고, "구글 지도에서 이 가게를 찾을 수 없습니다"를 상태 줄에 표시한다 |
| 캐싱 (만료 없음) | 조회에 성공하면 결과를 브라우저 `localStorage`에 `place-google-reviews:{카카오 place id}` 키로 저장한다. 같은 가게에서 "리뷰 보기"를 다시 누르면 로딩 텍스트 없이 캐시된 값을 즉시 보여준다 — TTL은 두지 않았다(요청대로 "한 번 조회하면 계속 기억"). "못 찾음" 결과는 캐시하지 않는다(좌표 스냅샷이나 구글 쪽의 일시적 문제일 수 있어, 재시도가 영구히 막히지 않게 하기 위함) |
| 카드 패턴 | 리뷰 카드는 6.11절 "재사용 가능한 카드 패턴"의 그림자·곡률 값을 그대로 따른다 |
| 접근성 | 별점은 `★` 기호와 함께 숫자를 항상 병기해 색상에만 의존하지 않는다. 상태 줄은 6.12절의 다른 섹션들과 동일하게 `role="status" aria-live="polite"`를 쓴다 |
| API 계약 | `day4/CLAUDE.md`의 `/api/day4/place-reviews` 절 참고 |
| 구현 | `day4/place.html`의 `initPlacePage()` 안에 인라인 작성 — `place.id`가 유효할 때만 초기화되는 기존 규칙을 그대로 따른다 |

| 위치 | `#search-results-list`의 각 카드(`renderPlaceCard`) 우상단, 카드에 절대 위치(`absolute right-4 top-4`)로 얹은 원형 아이콘 버튼 — 6.11절 카드 패턴의 본문 레이아웃은 그대로 두고 카드에만 `relative`를 추가했다. 6.17절 인기 랭킹 카드(`renderPopularCard`)에도 같은 자리에 같은 버튼을 붙였다(좌상단 순위 배지와 자리가 겹치지 않는다). `place.html` 가게 상세 헤더에도 비슷한 위치(`absolute right-5 top-6`)로 별도 구현했다 — 자세한 내용은 6.12절 참고 |

| 테이블/RLS | `day4/CLAUDE.md`의 "`place_saves` 테이블" 절 참고 |
| 영향 범위 | 처음엔 검색 결과 카드에만 있었으나, 이후 인기 랭킹 카드(6.17절)와 `place.html` 가게 상세 헤더(6.12절)까지 넓혔다 — 세 곳 모두 로직은 거의 동일하되, `place.html`은 자체 완결 원칙 때문에 index.html의 `setSaveButtonState`/클릭 핸들러를 그대로 복붙했다(공유 안 함) |

### 6.19 Web Interface Guidelines 점검 (2026-08-25)
> `web-design-guidelines` 스킬(vercel-labs/agent-skills)로 `index.html`/`place.html`/`mypage.html`/`auth.js` 4개 파일을 점검하고 나온 지적을 전부 반영했다. 원 지적 목록은 이 스킬 실행 대화 기록에 있고, 여기서는 실제로 코드가 바뀐 지점만 요약한다.

| 영역 | 무엇을 바꿨나 |
|---|---|
| 포커스 링 (가장 중요) | `auth.js` 로그인 모달의 이메일/비밀번호 input에 있던 `focus-visible:outline-none`을 지웠다. Tailwind 클래스 명시도(specificity)가 각 페이지의 `input:focus-visible{outline:3px solid...}` 규칙보다 높아서, 사실상 **세 페이지 전부의 로그인 모달에서 키보드 포커스 링이 안 보이는 상태**였다. auth.js는 어느 페이지에 삽입될지 몰라 호스트 페이지 CSS에 기대지 않고, 모달 자체에 `#auth-dialog input:focus-visible{...}` 스코프 스타일을 갖게 했다 |
| `transition-all` 제거 | 6.11절 카드 패턴과 CTA 버튼 전반에 쓰이던 `transition-all`을 실제로 바뀌는 속성만 나열한 `transition-[transform,box-shadow]` / `transition-[transform,background-color,box-shadow]`로 바꿨다(6.11절 패턴 정의 자체도 갱신) |
| `mypage.html` 삭제 확인 | X 버튼이 확인 없이 바로 지우던 것을, place.html과 같은 인라인 2단계 확인("정말 뺄까요? [빼기][취소]")으로 바꿨다(위 6.16절 표 참고) |
| `mypage.html` 헤딩 계층 | `<h1>` 다음 카드 제목이 `<h2>` 없이 바로 `<h3>`였던 걸, `sr-only` `<h2 id="saved-list-title">담은 가게 목록</h2>`을 목록 앞에 추가해 고쳤다(시각적으로는 h1 아래 안내 문구가 이미 같은 내용을 전달하므로 화면엔 안 보이게만) |
| 날짜 포맷 | `mypage.html`의 `formatSavedDate()`, `place.html`의 `timeAgo()` 둘 다 손으로 짠 포맷 대신 `Intl.DateTimeFormat`/`Intl.RelativeTimeFormat`을 쓰도록 바꿨다(`timeAgo`는 `numeric:'always'`로 고정 — `'auto'`면 "1년 전"이 "작년"처럼 관용구로 바뀌어 기존 표기 스타일이 깨진다) |
| 폼 필드 | `place.html`의 `#contribute-author`/`#contribute-photo`/`#contribute-text`/핀 range 두 개에 `name` 속성을 추가했다(기존엔 없었다 — JS가 `.value`로 직접 읽어서 동작엔 문제없었지만 폼 시맨틱·자동완성 관점에서 누락이었다). 빈 설명 제출 시 안내를 토스트 대신 필드 바로 아래 인라인 에러(`#contribute-text-error`)로 바꿨다 |
| 검색 URL 동기화 | `index.html` 검색이 `?q=` 쿼리스트링에 반영되도록 `history.pushState`를 추가했다 — 새로고침·뒤로가기·링크 공유로 같은 검색 결과를 다시 볼 수 있다. `popstate`도 처리한다 |
| 타이포그래피 | `index.html`의 후기·인용 문구에 쓰인 직선 따옴표(`"..."`)를 곡선 따옴표(`"..."`)로, `place.html`의 `"AI가 리뷰를 분석 하는 중..."`과 사진 URL placeholder의 `...`을 `…`로 바꿨다 |
| 성능/기타 | `index.html` `<head>`에 `cdn.jsdelivr.net`/`cdn.tailwindcss.com` `preconnect`와 `theme-color` 메타를 추가했다. `place.html`의 사진 `<img>` 두 곳(미리보기·제보 사진)에 `width`/`height` 속성을 추가했다(레이아웃 시프트 방지 — 다만 이미 `h-32`/`h-56` CSS 높이가 고정돼 있어 실제 체감 효과는 크지 않다). 인기 랭킹 순위 배지에 `aria-label="N위"`를 추가했다 |
| 그대로 둔 것 | `place.html`의 `#pin-picker` 클릭 div는 `aria-hidden="true"`이고 바로 옆 range 입력 두 개가 키보드 대안이라 문제없다고 판단해 그대로 뒀다. 다크 모드는 이 서비스의 색상 체계(2장) 자체가 라이트 전용으로 설계돼 있어 손대지 않았다 |

### 6.20 랜딩페이지 섹션 재배치·버튼 통일·"최근 리뷰" 개편 (2026-08-25)
> `index.html` 랜딩페이지 구성을 다시 손봤다. 세 가지가 한 번에 바뀌었다: (1) "먼저 다녀온 사람들이 남긴 길찾기"를 인기 랭킹 위로 옮김, (2) 카드 버튼 두 개(노란 CTA/보조 링크)의 라벨·링크를 통일, (3) "최근 리뷰" 섹션을 리뷰가 아니라 "최근 등록된 길찾기" 활동 피드로 바꾸고 별점을 없앰.

| 항목 | 내용 |
|---|---|
| 섹션 재배치 | "먼저 다녀온 사람들이 남긴 길찾기"(예전 "3. 길찾기")가 히어로 → 검색 결과 다음, 인기 랭킹보다 위로 옮겨왔다. 최종 순서: 1 히어로 → 1.5 검색 결과 → **1.6 먼저 다녀온 사람들이 남긴 길찾기** → 1.7 지금 인기 맛집 TOP 5 → 1.8 나를 위한 추천 → 2 문제 공감 → 3 작동 방식 → 4 최근 등록된 길찾기 → 5 신뢰/차별점 → 6 서비스 특징 → 7 푸터. 뒤 섹션들(작동 방식~푸터)은 번호만 하나씩 당겨졌을 뿐 내용은 그대로다 — 6.17/6.18절 본문의 절 번호 언급도 이에 맞춰 고쳤다 |
| 버튼 라벨·링크 통일 | 검색 결과·인기 랭킹·나를 위한 추천·길찾기 예시 카드 등 "가게 카드"에서 노란 CTA 버튼과 그 아래 보조 링크가 뜻하는 바가 제각각이었다(카카오맵 링크가 노란 버튼이었다가, 어떤 카드는 상세 페이지가 노란 버튼이었다가). 지금은 전부 통일했다: **노란 CTA 버튼 = "길찾기" = `place.html` 가게 상세 페이지로 이동**(내부 링크라 `target="_blank"` 없음), **그 아래 보조 밑줄 링크 = "카카오맵에서 보기" = 카카오맵 외부 링크**(`target="_blank" rel="noopener"` 유지). `renderPlaceCard()`(검색 결과·나를 위한 추천 공용)와 1.6절 예시 카드 5개 모두 이 규칙을 따른다. 인기 랭킹 카드(`renderPopularCard`)는 원래 카카오맵 버튼이 없어서(응답에 `url` 필드가 없음) 손대지 않았다 — "가게 상세 보기" 링크 하나만 그대로 있다 |
| "최근 등록된 길찾기"로 개편 | 원래 "5. 최근 리뷰"는 사실 리뷰가 아니라 그냥 감성적인 한 줄 후기 티커였다(별점 + 인용구 + "동네 가게명 · 닉네임"). 리뷰 작성 기능 자체가 없다는 게 이름과 안 맞아서, "최근 등록된 길찾기"로 이름과 내용을 모두 바꿨다. **별점(★)과 "별점 X.X" 텍스트는 완전히 제거했다** — 이 서비스에 평점 개념 자체가 없다(구글 리뷰 평점은 place.html 안의 별개 기능, 6.13절). 흐름 정지 버튼 라벨도 "리뷰 흐름 멈추기"→"흐름 멈추기"로, id도 `review-title`→`recent-updates-title`로 바꿨다. 이 단계에서는 여전히 예시(더미) 데이터였는데, 바로 다음 절(6.21)에서 실제 DB 데이터로 다시 한번 바뀐다 |
| 안 바꾼 것 | 티커의 애니메이션·정지 로직(`prefers-reduced-motion` 대응 포함), 가로 스크롤 캐러셀 CSS는 그대로다. 3.x절이 정의한 8개 섹션 → 지금은 검색 결과·인기 랭킹·추천까지 더해 11개 섹션이 됐지만, 이 절은 그 히스토리를 다시 쓰지 않고 6.11절부터 이어지는 "무엇이 바뀌었나"만 기록한다 |

### 6.21 "최근 등록된 길찾기" 실데이터 전환 + 핀 신고 (`day4/index.html`, `day4/place.html`) (2026-08-25)
> 6.20절에서 별점만 뺀 "최근 등록된 길찾기"가 여전히 예시(더미) 데이터였는데, 사용자가 "예시 말고 실제 데이터로 보여줘"라고 요청해 그 자리에서 바로 한 번 더 바뀌었다. 곁들여 5개 예시 가게(1.6절 캐러셀과 같은 가게들)에 `place_info_entries` 더미를 실제로 등록했다.

| 항목 | 내용 |
|---|---|
| 문제 | `place_info_entries`는 원래 가게 이름을 모른다(`place_id`만 있음) — 특정 가게 하나를 조회할 땐 `place.html`이 쿼리스트링으로 이미 이름을 알고 있어 상관없었지만, "전체 가게를 통틀어 최신 N건"을 보여주는 피드는 각 행이 어느 가게인지 스스로 알아야 한다 |
| 해결 — 비정규화 컬럼 | `place_info_entries`에 `place_name`/`category`/`address` 컬럼을 추가했다(`place_saves`가 이미 쓰고 있는 것과 같은 패턴 — 라이브 조인 대신 등록 시점 스냅샷을 그대로 저장). `POST /api/day4/place-info`가 이 세 필드를 선택적으로 받아 저장하고, `place.html`의 제출 요청이 이미 알고 있는 `place.name`/`place.category`/`place.address`를 그대로 실어 보낸다. 자세한 계약은 `day4/CLAUDE.md`의 "`/api/day4/place-info` 계약"·"테이블 스키마" 참고 |
| 새 엔드포인트 | `GET /api/day4/place-info-recent` — 특정 가게가 아니라 전체에서 `created_at` 내림차순 최신 12건. `place_name is null`인 행(컬럼 추가 이전의 옛 데이터)은 제외한다. `server.js`/`api/day4/place-info-recent.js`(신규 Vercel 미러) 둘 다 구현했다 |
| `index.html` 쪽 변화 | 티커의 정적 `<li>` 12개(6개 예시 + aria-hidden 사본 6개)를 전부 지우고, `#ticker-list`(빈 `<ul>`)로 바꿨다. 페이지 로드 시(로그인 여부 무관, `Day4Auth` 필요 없는 순수 공개 API라 module 스크립트를 기다리지 않고 classic 스크립트에서 바로) `loadRecentUpdates()`가 `/api/day4/place-info-recent`를 불러 카드를 두 벌(실제 절반 + `aria-hidden` 사본 절반) 렌더링한다 — 6.11절 이후 계속 써온 "앞 절반 + 뒤쪽 aria-hidden 사본"이라는 무한 스크롤 구조 자체는 그대로, 내용만 정적에서 동적으로 바뀌었다 |
| 카드 내용 | "가게이름 · 카테고리"(굵은 테라코타) + `"{등록된 설명 텍스트}"`(`line-clamp-3`로 긴 설명 3줄까지만) + "N분 전 · 작성자"(`Intl.RelativeTimeFormat`, `numeric: 'always'` 고정 — place.html의 `timeAgo()`와 같은 이유로 "어제"류 관용구를 피한다). `text`는 서버가 등록 시점에 필수값으로 강제하므로(`MISSING_TEXT`) 이 피드에서 빈 설명을 걱정할 필요는 없다 |
| 빈 결과·오류 | 서버 오류거나 아직 아무 것도 없으면 `#recent-updates-status`에 "아직 등록된 길찾기가 없어요. 먼저 남겨보세요!"만 보여주고 티커 자체(`#ticker`)는 `hidden` 상태를 유지한다 — 빈 캐러셀이 스크롤되는 것보다 낫다고 판단 |
| 5개 예시 가게 더미 등록 | 1.6절 캐러셀과 같은 가게(네시사분·원조만선호프·밀도 성수본점·정돈 강남점·희옥)에 실제 `POST /api/day4/place-info`로 등록했다(일회성 스크립트, 저장소에 남기지 않음 — day4/CLAUDE.md의 이미지 스크립트와 같은 관례). 설명 문구는 1.6절 캐러셀·6.20절 옛 더미 티커와 같은 것을 재사용했다 — 우연이 아니라 "이 예시 가게들이 실제로 이렇게 등록된 것처럼" 이야기가 이어지게 하려는 의도. 네시사분은 2건(핀 있음 1 + 텍스트만 1) 넣어서 한 가게에 여러 제보가 쌓이는 모습도 보여준다. 기존에 있던 옛 테스트 행 4개(2026-08-20~21에 남겨진, "4층 입니다." 같은 네시사분 테스트 데이터)는 사용자가 만든 것일 수 있어 지우지 않았다 — 새로 넣은 6건보다 오래돼 피드 뒤쪽에 자연스럽게 밀려난다 |
| 핀 신고와의 관계 | "핀 신고" 기능(`report_count`, 6.12절 표의 "핀 신고 (2026-08-25)" 행)은 이번 절과 **같은 날 있었던 별개 변경**이다 — `report_count` 마이그레이션이 먼저, `place_name`/`category`/`address` 마이그레이션이 나중이라 결과적으로 `place_info_entries`에 이날 하루에만 컬럼이 두 번 추가됐다. 헷갈리지 않도록 정리: `report_count`는 6.12절, `place_name`/`category`/`address`는 이번 절(6.21) |
