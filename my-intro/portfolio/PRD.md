## 1. 개요

`my-intro` 리포지토리에 흩어져 있는 작업물을 한 곳에 모아 보여주는 **개인 프로젝트 허브**. 인트로 화면에서 엔터를 눌러 진입하면 프로젝트 카드 목록이 나타나고, 카드를 열면 그 프로젝트를 왜 만들었고 어떻게 풀었는지가 케이스 스터디로 펼쳐진다.

지금은 프로젝트마다 개별 HTML 파일로만 존재해 **진입점이 없다.** 채용 담당자에게 작업물을 보내려면 파일 여러 개를 나열하고 각각을 말로 설명해야 한다. 게다가 결과 화면만 봐서는 무엇을 고민해서 그렇게 만들었는지가 드러나지 않는다.

### 한 줄 정의

> 링크 하나로 내가 만든 것과 그렇게 만든 이유까지 전달하는 작업 보관소.

## 2. 문제 정의와 목표

### 해결하려는 문제

| 문제 | 현재 상황 | 제품의 해결 방식 |
|---|---|---|
| 작업물에 진입점이 없다 | 파일 경로를 하나씩 안내 | 링크 하나에서 전체를 탐색 |
| 결과만 보이고 과정이 안 보인다 | 완성된 화면만 존재 | 카드별 케이스 스터디(문제·접근·구현·결과) |
| 무엇을 할 줄 아는지 판단이 어렵다 | 코드를 열어봐야 알 수 있음 | 카드에 기술 스택·역할·기간 명시 |
| 작업이 늘어도 정리가 안 된다 | 폴더만 늘어남 | 데이터 배열에 항목 하나 추가로 확장 |

### 성공 기준 (v1)

- 채용 담당자가 **첫 화면 진입 후 10초 안에** 프로젝트 4개의 존재와 성격을 파악한다.
- 카드 하나를 열어 **1분 안에** 그 프로젝트의 문제의식과 해결 방식을 읽어낸다.
- 어느 카드에서든 **클릭 한 번으로** 실제 동작하는 페이지에 도달한다.
- 프로젝트를 추가할 때 **HTML 구조를 건드리지 않고** 데이터 배열에만 항목을 더한다.

### 비목표 (v1에서 하지 않는 것)

- 백엔드, 데이터베이스, 관리자 화면
- 방문자 통계·분석 도구 연동
- 다국어(영문) 버전
- 블로그·글 목록 등 프로젝트 외 콘텐츠
- 검색·태그 필터 (프로젝트 4개 규모에서는 불필요)

## 3. 대상 사용자

**주 사용자: 채용 담당자 · 면접관**

- 이력서나 메일에 첨부된 링크를 클릭해 들어온다
- 여러 지원자의 포트폴리오를 연속으로 훑는 중이다 — **체류 시간은 1~3분**
- 결과물의 완성도보다 **어떻게 판단하고 무엇을 배웠는지**를 본다
- 주로 데스크톱 브라우저, 면접 직전 확인 시 모바일

**부차 사용자: 작성자 본인**

- 지금까지 만든 것을 한눈에 보고 다음 작업을 정한다
- 면접장에서 화면을 띄워놓고 설명하는 자료로 쓴다

**사용 맥락:** 로컬 `file://`로 열어 확인하거나, 정적 호스팅에 올려 링크로 공유한다. 오프라인에서도 열람 가능해야 한다.

## 5. 기능 요구사항

### FR-1 인트로 화면

- FR-1.1 첫 진입 시 뷰포트 전체를 채우는 인트로를 표시한다. 중앙에 서비스명 `ARCHIVE / 아카이브`와 한 줄 소개, 진입 버튼을 둔다.
- FR-1.1a 인트로는 **보랏빛 어두운 바탕**이며, 배경에 커다란 블러 그라디언트 블롭 3개가 서로 다른 주기로 천천히 떠다닌다. 그 위에 옅은 노이즈 결을 얹는다. **리스트도 같은 블롭·노이즈를 공유하되 더 뒤로 물린다.**
- FR-1.1b 제목·소개는 **한 줄씩 아래에서 위로 마스크 리빌**되며 등장한다. 진입 버튼과 힌트는 줄이 모두 올라온 뒤 따라 나온다.
- FR-1.1c 리빌의 초기 상태는 **스크립트로만 지정한다.** 스타일시트에 숨김을 박아두면 스크립트 실패 시 제목이 영영 보이지 않는다.
- FR-1.2 진입 트리거는 **세 가지 모두** 지원한다 — `Enter` 키, 진입 버튼 클릭, 아래 방향 스크롤/스와이프.
- FR-1.3 진입 버튼에는 키보드 힌트(`PRESS ENTER`)를 함께 표기해 조작 방법을 노출한다.
- FR-1.4 인트로 진입 후 3초간 조작이 없으면 힌트에 은은한 반복 애니메이션을 주어 다음 행동을 유도한다.
- FR-1.5 리스트에서 인트로로 되돌아가는 경로를 제공한다(헤더의 로고 클릭).

### FR-2 화면 전환

- FR-2.1 인트로 → 리스트 전환에 **크로스페이드**를 사용한다. 인트로가 살짝 커지며 물러나 사라지고, 리스트가 아주 조금 확대된 상태에서 제자리를 찾은 뒤 카드가 차례로 떠오른다.
- FR-2.2 구간은 셋을 겹쳐 배치한다 — 인트로 퇴장(`opacity 1→0`, `scale 1→1.06`, 800ms, `power2.in`, 0s) · 리스트 등장(`opacity 0→1`, `scale 1.03→1`, 1200ms, `expo.out`, 0.25s) · 카드 등장(`y 54→0`, 1300ms, 간격 100ms, 0.4s).
- FR-2.3 **튕기거나 되돌아오는 움직임을 쓰지 않는다.** `expo.out`은 초반에 크게 움직이고 끝이 길게 늘어져 멎으므로 가볍게 보이지 않는다.
- FR-2.4 전환 중에는 **떠나는 화면만** 뷰포트에 고정해 위로 겹친다. 남는 화면은 흐름에 그대로 둔다 — 변환이 걸린 조상 안에서는 고정 헤더가 뷰포트 기준을 잃기 때문이다.
- FR-2.5 **애니메이션 라이브러리 로드에 실패하면 전환 없이 즉시 리스트를 표시한다.** 화면이 중간 상태로 멈춰서는 안 된다.
- FR-2.6 JavaScript가 비활성화된 환경에서는 인트로를 건너뛰고 리스트를 바로 표시한다(`<noscript>` 처리).
- FR-2.7 `prefers-reduced-motion: reduce`일 때 전환 애니메이션을 생략하고 즉시 화면을 교체한다.

### FR-3 프로젝트 리스트

- FR-3.1 프로젝트를 카드 그리드로 배치한다. 데스크톱 2열, 그 외 1열. **3열 이상으로 늘리지 않는다** — 유리 카드가 작아지면 떠 있는 느낌과 마우스 반응이 모두 죽는다.
- FR-3.2 카드는 데이터 배열 순서대로 렌더링한다. 순서는 **최신 작업이 앞**이다.
- FR-3.3 리스트 상단에 고정 헤더를 둔다. 헤더에는 로고와 연락 수단(메일 등)을 배치한다.
- FR-3.4 카드는 화면 진입 시 **차례로 떠오르며 등장한다**(FR-2.2의 마지막 구간). 초기 상태는 **스크립트로만 지정한다** — 스타일시트에 숨김을 박아두면 스크립트 실패 시 카드가 영영 보이지 않는다.
- FR-3.5 카드는 등장 후 **각자 다른 주기로 계속 떠 있는다**(`y` 9~16px, 3.4~5.8초, 무한 `yoyo`). 주기와 시작 지연을 어긋나게 잡아 넷이 함께 오르내리지 않게 한다.
- FR-3.6 카드는 **포인터 위치에 따라 살짝 기운다**(좌우 ±3.2°, 상하 ∓2.4°, 카드마다 깊이 차등). `mousemove`마다 트윈을 새로 만들지 않고 재사용 가능한 세터로 구현한다. **터치 기기에서는 적용하지 않는다.**
- FR-3.7 하단 푸터에 작성 연도와 저장소 링크를 표기한다.

### FR-4 프로젝트 카드

카드는 **반투명 유리**이며, 스크린샷 없이 **타이포만으로** 프로젝트를 미리 보여준다.

| 항목 | 예시 |
|---|---|
| 번호 | `01` (가늘고 넓은 큰 숫자, 포인트 색) |
| 제목 | 모의고사 연습장 |
| 부제 | Answer Sheet (자간을 넓힌 작은 라벨) |
| 한 줄 소개 | 내 기출문제를 넣으면 시험지가 되는 개인 연습장 |
| 기술 스택 | HTML · CSS · JavaScript · localStorage |

- FR-4.1 카드 전체가 클릭 영역이며, 클릭 시 해당 프로젝트의 상세 모달을 연다.
- FR-4.2 카드는 키보드로 접근 가능해야 한다(`Tab` 이동, `Enter`/`Space`로 열기).
- FR-4.3 **카드에 스크린샷을 넣지 않는다.** 유리 위에 사진을 얹으면 뒤의 광원과 겹쳐 지저분해진다. 스크린샷은 상세 모달에서 크게 본다(FR-5). 모달에서 썸네일이 없는 프로젝트는 번호와 제목으로 된 대체 표시를 렌더링한다.
- FR-4.4 기술 스택은 태그 형태로 표시하며 최대 5개까지 노출한다.
- FR-4.5 카드는 부유(`y`)와 기울기(`rotation`)를 **서로 다른 요소에 건다.** 한 요소에 둘을 걸면 transform이 서로를 덮어쓴다.

### FR-5 상세 모달 (케이스 스터디)

모달 본문은 다음 순서로 구성한다.

| 블록 | 내용 |
|---|---|
| 헤더 | 번호, 제목, 부제, 닫기 버튼 |
| 썸네일 | 대표 화면 |
| 메타 | 제작 기간, 역할, 기술 스택 |
| **문제** | 왜 만들었는가 — 해결하려던 상황 |
| **접근** | 어떤 방향으로 풀기로 했는가 |
| **구현 포인트** | 기술적으로 판단이 필요했던 지점 2~3개 |
| **결과 / 배운 점** | 무엇이 되었고 무엇을 알게 되었는가 |
| 액션 | `라이브 보기` · `소스 보기` |

- FR-5.1 모달은 배경 클릭, `ESC` 키, 닫기 버튼 세 가지로 닫는다.
- FR-5.2 모달이 열린 동안 배경 스크롤을 잠근다. 닫으면 **리스트의 스크롤 위치를 그대로 복원**한다.
- FR-5.3 모달이 열리면 포커스를 모달 안으로 옮기고, `Tab` 순환을 모달 내부로 가둔다. 닫으면 **직전에 클릭했던 카드로 포커스를 되돌린다.**
- FR-5.4 `role="dialog"`, `aria-modal="true"`, `aria-labelledby`로 제목과 연결한다.
- FR-5.5 본문이 길면 모달 내부에서만 스크롤한다. 페이지 본문이 함께 움직이지 않는다.
- FR-5.6 구현 포인트가 없는 프로젝트는 해당 블록을 렌더링하지 않는다. 빈 제목만 남기지 않는다.

### FR-6 라이브 · 소스 링크

- FR-6.1 `라이브 보기`는 해당 프로젝트 HTML을 **새 탭**으로 연다(`target="_blank"`, `rel="noopener"`).
- FR-6.2 링크는 리포지토리 기준 상대 경로로 작성한다(예: `../day2/index.html`). 로컬과 호스팅 양쪽에서 동작해야 한다.
- FR-6.3 소스 링크가 없는 프로젝트는 해당 버튼을 렌더링하지 않는다. 비활성 버튼을 남기지 않는다.

### FR-7 반응형 · 접근성

- FR-7.1 320px 폭까지 가로 스크롤 없이 표시한다.
- FR-7.2 모든 상호작용 요소에 `:focus-visible` 표시를 제공한다.
- FR-7.3 본문 텍스트와 배경의 명도 대비는 WCAG AA(4.5:1)를 만족한다.
- FR-7.4 터치 대상은 최소 44×44px을 확보한다.
- FR-7.5 이미지에는 내용을 설명하는 `alt`를 부여한다. 장식 요소는 `aria-hidden="true"` 처리한다.
- FR-7.6 `prefers-reduced-motion: reduce`일 때 모든 애니메이션과 부드러운 스크롤을 비활성화한다.

## 6. 콘텐츠 모델

프로젝트 데이터는 스크립트 상단의 **`PROJECTS` 배열** 하나에 모은다. 나머지 코드는 이 배열을 읽어 렌더링만 한다. 프로젝트 추가는 배열 항목 추가로 끝난다.

`day1/fortune.html`이 `FORTUNES` 배열에 데이터를 모아두고 나머지를 프레젠테이션으로 둔 것과 같은 구조다.

### 스키마

```js
{
  id:        'exam',                    // 고유 식별자 (모달 앵커·DOM id에 사용)
  no:        '01',                      // 카드에 표시할 번호
  title:     '모의고사 연습장',
  subtitle:  'Answer Sheet',
  tagline:   '내 기출문제를 넣으면 시험지가 되는 개인 연습장',
  period:    '2026.08',
  role:      '기획 · 디자인 · 개발 전체',
  stack:     ['HTML', 'CSS', 'JavaScript', 'localStorage'],
  thumb:     'thumbs/exam.png',         // 없으면 null → 대체 표시 (FR-4.3)
  liveUrl:   '../day2/index.html',
  sourceUrl: '../day2/index.html',      // 없으면 null → 버튼 미렌더 (FR-6.3)
  study: {
    problem:    '...',                  // 문제
    approach:   '...',                  // 접근
    highlights: ['...', '...'],         // 구현 포인트 (빈 배열이면 블록 생략)
    result:     '...'                   // 결과 / 배운 점
  }
}
```

### v1 수록 항목 (4개)

#### 01 · 모의고사 연습장 (Answer Sheet) — `../day2/index.html`

| 필드 | 값 |
|---|---|
| 한 줄 소개 | 내 기출문제를 넣으면 시험지가 되고, 틀린 문제는 저절로 오답노트가 되는 개인 연습장 |
| 스택 | HTML · CSS · JavaScript · localStorage |
| 역할 | 기획 · 디자인 · 개발 전체 |

- **문제** — 자격증 기출 PDF는 확보했는데 반복해서 풀 방법이 없었다. 시중 문제은행에는 원하는 자격증이 없거나, 있어도 내가 가진 자료를 넣을 수 없었다.
- **접근** — 문제 콘텐츠는 사용자가 소유하고, 앱은 **출제·채점·오답 추적만** 담당하도록 역할을 갈랐다. 계정도 서버도 두지 않았다.
- **구현 포인트**
  - 이미지를 문제별 개별 키(`img:{examId}:{questionId}`)로 저장해 **localStorage 항목당 5MB 한도를 우회**했다. 문제 배열에 인라인하면 이미지 몇 개만에 저장이 깨진다.
  - 오답노트를 **연속 2회 정답 시 자동 제외**로 설계했다. 1회는 우연히 맞을 수 있고, 3회는 노트가 비워지지 않는다.
  - 샌드박스 환경에서 `confirm`/`prompt`가 차단되면 화면이 멈춘 것처럼 보여, Promise 기반 다이얼로그로 전부 대체했다.
- **결과 / 배운 점** — PRD와 디자인 토큰 문서를 먼저 쓰고 구현한 유일한 프로젝트다. **브라우저 저장소의 물리적 한계가 데이터 모델을 결정한다**는 것을 배웠다. PDF 자동 추출(FR-2)은 API 키를 둘 곳이 없어 의도적으로 남겨두고, 그 사실을 문서에 명시했다.

#### 02 · 아리랑시네센터 — `../day3/index2.html`

| 필드 | 값 |
|---|---|
| 한 줄 소개 | 국내 최초 공립영화관을 동네 극장의 언어로 소개하는 랜딩 페이지 |
| 스택 | HTML · CSS · JavaScript |
| 역할 | 정보 구조 · 디자인 · 개발 |

- **문제** — 실존하는 공공기관(성북구 아리랑시네센터)을 소개해야 했다. 공공기관 페이지는 정보를 나열하다 딱딱해지기 쉬운데, 정작 전하고 싶은 것은 "가까운 동네 극장"이라는 감각이었다.
- **접근** — 기관 소개가 아니라 **"이런 곳입니다"라는 성격 서술**을 축으로 잡았다. 개관 연도·상영관 수·독립영화전용관 같은 숫자를 앞세워 신뢰를 주고, 예매처럼 자주 바뀌는 정보는 공식 홈페이지로 넘겼다.
- **구현 포인트**
  - 상영 시간표·예매를 페이지에 담지 않고 공식 홈페이지로 연결했다. **정적 페이지가 감당할 수 없는 정보를 떠안지 않기 위해서**다.
  - 의존성 없이 단일 HTML 13.5KB로 완결했다.
- **결과 / 배운 점** — 실제로 존재하는 대상을 다룰 때는 **무엇을 싣지 않을지 정하는 일**이 먼저라는 것을 배웠다.

#### 03 · LIFTOFF 랜딩페이지 — `../day3/landing page.html`

| 필드 | 값 |
|---|---|
| 한 줄 소개 | 지역 창작자 행사 랜딩 — 인터랙션을 가장 깊게 다뤄본 페이지 |
| 스택 | HTML · Tailwind CSS · JavaScript · GSAP |
| 역할 | 디자인 · 인터랙션 · 개발 |

- **문제** — 행사 랜딩에 움직임을 넣되, 장식으로 겉돌지 않고 **읽는 흐름을 도와야** 했다. 초기 버전은 고정 헤더의 가장자리가 화면 중간에서 잘려 보이고, 모바일에는 내비게이션이 아예 없었다.
- **접근** — 움직임을 세 층으로 나눴다. **진입**(커브 스와이프), **스크롤 반응**(헤더 상태 변화·카드 등장), **입력 피드백**(클릭 파티클). 각 층이 서로 다른 목적을 갖게 했다.
- **구현 포인트**
  - `position: fixed` 요소에 `mx-auto`가 먹지 않아 헤더가 왼쪽에 붙고 오른쪽이 잘려 있었다. **고정 레이어와 콘텐츠 컨테이너를 분리**해 해결했다.
  - 커브 스와이프는 진행도 `p` 하나만 트윈하고, 가장자리 `x = p×100`·휨 `= sin(p×π)×22`로 SVG path를 매 프레임 재생성한다. 값 하나로 위치와 곡률이 동시에 결정된다.
  - 스크롤 등장 효과는 JS가 클래스를 부여하는 방식이라 **스크립트가 실패해도 콘텐츠가 사라지지 않는다.** 터치 기기에서는 `hover` 확대가 손을 떼도 남아 `@media (hover: none)`으로 껐다.
  - GSAP 로드 실패·`prefers-reduced-motion` 각각에 폴백을 뒀다.
- **결과 / 배운 점** — 애니메이션에서 정작 시간이 드는 것은 효과 자체가 아니라 **실패했을 때의 상태를 설계하는 일**이었다. 막이 걷히지 않으면 페이지 전체가 잠긴다.

#### 04 · 오늘의 운세 — `../day1/fortune.html`

| 필드 | 값 |
|---|---|
| 한 줄 소개 | 카드 한 장을 뽑으면 오늘의 메시지가 열리는 작은 페이지 |
| 스택 | HTML · CSS · JavaScript |
| 역할 | 기획 · 디자인 · 개발 전체 |

- **문제** — 사용자가 "무언가 했다"는 감각을 남기는 작은 인터랙션을 만들어보고 싶었다. 결과를 그냥 보여주면 읽고 끝이지만, **직접 고르게 하면 그 결과가 자기 것이 된다.**
- **접근** — 뽑기라는 최소 단위의 선택을 넣었다. 카드를 고르면 행운의 색·숫자·키워드가 열리고, 다시 뽑을 수 있다.

  - 외부 의존성 없이 CSS·JS를 모두 인라인해 파일 하나로 완결했다.
- **결과 / 배운 점** — 이 배열 구조가 마음에 들어 **ARCHIVE의 `PROJECTS` 배열도 같은 방식으로 설계**했다.

## 8. 설계 결정 및 근거

| 결정 | 근거 | 대안 |
|---|---|---|
| 단일 `index.html` + 인라인 CSS/JS | day1~day4가 모두 단일 HTML 패턴. `file://`로 열어도 그대로 동작 | 파일 분리, 번들러 도입 |
| 상세를 별도 페이지가 아닌 모달로 | 닫았을 때 보던 카드 위치가 유지됨. 파일 수가 늘지 않음 | 프로젝트별 상세 HTML |
| 인트로를 별도 화면으로 분리 | "들어간다"는 의식이 생기고, 이름을 각인시킬 자리가 생김 | 스크롤로 이어지는 한 장 |
| 진입 트리거를 3가지 지원 | 엔터만 두면 못 찾고 이탈한다. 클릭·스크롤이 안전망 | 엔터 전용 |
| 전환을 크로스페이드로 | 튕기거나 미끄러지는 전환은 가볍게 읽힌다. 물러나고 다가오는 움직임에 `expo.out`을 걸면 끝이 길게 늘어져 무게가 생긴다 | 푸터 바운스(경박함), 커브 스와이프(day3에 이미 있음) |
| 카드에서 썸네일을 뺌 | 유리 위에 사진을 얹으면 뒤의 광원과 겹쳐 지저분해진다. 타이포만 남기면 유리의 성격이 살고, 스크린샷은 모달에서 더 크게 볼 수 있다 | 카드에 썸네일 유지, 썸네일을 유리 뒤 배경으로 |
| 부유와 기울기를 두 요소로 분리 | 한 요소에 걸면 transform이 서로를 덮어쓴다 | 하나로 합쳐 매 프레임 행렬 합성 |
| GSAP CDN 사용 + 폴백 필수 | 루트 `CLAUDE.md`의 "no dependencies"와 충돌하나 day3에 선례가 있음. **막이 걷히지 않으면 페이지 전체가 잠기므로** 폴백이 조건 | 자체 rAF 구현, 라이브러리 없음 |
| `PROJECTS` 배열로 데이터 분리 | `day1/fortune.html`의 `FORTUNES`와 같은 패턴. 확장이 항목 추가로 끝남 | HTML에 직접 마크업 |
| 카드 상세를 케이스 스터디로 | 타겟이 채용 담당자. 결과물보다 **사고과정이 판단 근거** | 스펙 요약, 스크린샷 갤러리 |
| 자기소개 성격 페이지 2개 제외 | ARCHIVE 자체가 그 역할. 같은 성격이 셋이면 중복 | 전부 수록 |
| 검색·필터 미도입 | 4개 규모에서는 스크롤이 더 빠름 | 태그 필터 |
